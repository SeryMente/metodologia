## 2\. Arquitectura de Backblaze

### 2.1. EP: arquitectura propuesta

EP aún no utiliza B2 mediante API S3-compatible ni mediante una CLI configurada y verificada en el entorno actual.

El modelo planteado es\:

`datos locales → snapshot coherente → manifiesto → B2 → verificación → recibo → restauración → verificación funcional`\.

El destino documentado es `OCP-MCP/ep-ocp/`\. Los identificadores lógicos de conjuntos, manifiestos, referencias a versiones remotas y mecanismo de sync todavía no están implementados.

No hay funciones EP verificadas de subida, descarga, listado, eliminación, cifrado ni lectura física de objetos.

### 2.2. Custodia: arquitectura implementada en la rama de PR

Custodia sí utiliza B2 mediante la **API S3-compatible**\. El adaptador utiliza `S3Client` de AWS SDK, con endpoint regional `s3.<region>.backblazeb2.com` y acceso estilo path. Backblaze documenta esa compatibilidad con la sintaxis S3. \[[S3-Compatible API](https://www.backblaze.com/docs/cloud-storage-s3-compatible-api?utm_source=chatgpt.com)\]

Las funciones relevantes implementadas en `object-storage.ts` son\:

| Función | Comportamiento |
|--------|--------|
| `storageLocation()` | Obtiene bucket y región de configuración |
| `b2Enabled()` | Selecciona B2 mediante `KHORA_OBJECT_STORAGE` |
| `createB2Client()` | Construye el cliente S3 con las credenciales configuradas |
| `fetchStoredObject()` | Lee B2 mediante GET firmado de corta duración; conserva lectura Blob heredada |
| `putEncryptedObject()` | Escribe objetos cifrados en B2 o usa Blob si B2 no está seleccionado |
| `prepareStagedUpload()` | Prepara una capacidad PUT firmada temporal |
| `isStagingObject()` | Valida que la referencia temporal corresponda a la sesión |
| `deleteStagedObject()` | Elimina versiones de objetos temporales autorizados |
| `listB2Objects()` | Lista objetos B2 con paginación limitada |

**Organización de objetos\:**

- Los objetos están bajo el prefijo `khora/`\.
- El staging de audio utiliza `khora/staging/audio/<sessionId>/...`\.
- La migración de audio Blob utiliza `khora/dictado/migrated/vercel-blob/<sha256-url>.khc`\.
- Las cargas ordinarias agregan un UUID aleatorio al nombre para evitar colisiones.
- Las referencias persistidas son localizadores B2 sin query string ni token firmado.
- Las URLs firmadas se generan temporalmente en el servidor; no forman parte del localizador persistente.

El adaptador pagina `ListObjectsV2` con hasta 1000 objetos por petición y tiene un límite de 10 000 objetos por llamada lógica. La migración de Blob usa cursores para enumerar páginas de origen, hasta el límite de páginas que impone el script.

**Límites relevantes\:** el adaptador no implementa carga multipart ni una cola de transferencias fuera de línea. Las cargas ordinarias reciben un `Buffer`; el staging firmado limita el tamaño a aproximadamente 24 MiB más el sobre. El migrador admite objetos cifrados de hasta 512 MiB, pero los carga completos en memoria. No es una solución de transferencia de archivos grandes con reanudación por partes.

El cliente S3 configura `maxAttempts: 3`; las lecturas HTTP tienen timeouts. Eso proporciona reintentos del SDK para determinadas peticiones, pero no equivale a una cola durable, a una transferencia multipart reanudable ni a pruebas demostradas de recuperación ante pérdida de red.

### 2.3. Autenticación y permisos

Custodia lee estas variables, sin que sea necesario revelar sus valores\:

- `KHORA_OBJECT_STORAGE`
- `KHORA_B2_BUCKET_NAME`
- `KHORA_B2_REGION`
- `KHORA_B2_KEY_ID`
- `KHORA_B2_APPLICATION_KEY`

La restricción efectiva de la clave **no la hace el código TypeScript**\. El adaptador valida que las claves de objeto estén bajo `khora/`, pero el alcance de acceso real depende de la configuración de la Application Key en Backblaze.

Backblaze permite restringir las claves estándar por bucket, prefijo y capacidades como lectura, listado y escritura. Recomienda separar claves por ámbito y no conceder borrado cuando la aplicación no lo necesita. \[[Cloud Storage Application Keys](https://www.backblaze.com/docs/cloud-storage-application-keys?utm_source=chatgpt.com); [Map IAM Policies and S3 ACLs to Backblaze B2 Access Controls](https://www.backblaze.com/docs/cloud-storage-map-iam-policies-and-s3-acls-to-backblaze-b2-access-controls?utm_source=chatgpt.com)\]

### 2.4. Cifrado

En Custodia hay dos capas\:

1. **Cifrado de aplicación KHC1\:** `lib/server/cripto.ts` utiliza AES-256-GCM. El sobre binario lleva la marca `KHC1`, un IV de 12 bytes, una etiqueta de autenticación de 16 bytes y el contenido cifrado. La clave deriva de `X_KHORA_KEY`\.
2. **Cifrado del lado del servidor\:** el adaptador y el migrador envían `ServerSideEncryption: "AES256"`, que corresponde al mecanismo SSE-B2 de Backblaze en la API S3-compatible. \[[Cloud Storage Server-Side Encryption](https://www.backblaze.com/docs/cloud-storage-server-side-encryption?utm_source=chatgpt.com); [S3-Compatible API](https://www.backblaze.com/docs/cloud-storage-s3-compatible-api?utm_source=chatgpt.com)\]

| Backblaze B2 | Bytes de los objetos de audio cifrados |
| Ledger `custodia_blob_b2_migration` | Estado de cada copia y repunte de referencias |
| Aplicación KHORA | Autorización, cifrado/descifrado y lectura de objetos |

El ledger 035 incluye origen, destino, hashes, tamaños, estado, ocurrencias, intentos y último error. Sus estados incluyen `pending`, `quarantined`, `copied_verified`, `references_updated` y `failed`\.

El migrador agrupa referencias de `dictado_audio_parte`, `dictado_mp3`, `dictado_mp3_historial`, `volcado.audio_url` y elementos JSONB en `volcado.audio_partes`\.

En EP, el OEP describe otra estructura: registro técnico local y libro mayor remoto con `ep_sessions`, `ep_bootstrap_tokens` y `ep_events`, con encadenamiento de SHA-256. Pero **el OEP no acredita que ese libro mayor esté conectado específicamente a Neon**, ni he encontrado una integración B2/Neon ejecutable de EP. Por eso no puedo afirmar que EP ya tenga una separación operativa entre datos en Neon y objetos en B2.

### 3.2. Objetos huérfanos, duplicados y consistencia

El migrador de Custodia tiene protecciones útiles\:

- Enumera el almacén Blob y agrupa sus referencias en la base de datos.
- Pone en cuarentena referencias con hashes o tamaños ausentes o contradictorios.
- Detecta referencias de base de datos que no aparecen en el listado físico de Blob.
- Usa una clave de destino determinista derivada del SHA-256 de la URL de origen.
- Verifica el objeto B2 antes de modificar referencias.
- Actualiza las referencias relacionales y JSONB en una transacción.
- Comprueba que no queden referencias al localizador de origen.
- Conserva siempre el Blob original.

La verificación física de B2 hace un GET del objeto, compara el SHA-256 de los bytes cifrados, comprueba el sobre KHC1, descifra y compara tamaño y SHA-256 del contenido en claro.

Hay, no obstante, límites importantes\:

- El migrador detecta referencias a objetos de Blob ausentes, pero no ofrece un inventario general y reconciliación exhaustiva de objetos B2 sin referencias.
- Agrupa duplicados por URL de origen, no por igualdad de contenido entre URLs distintas.
- Si la copia B2 se completa y falla la transacción Neon, puede quedar un objeto B2 sin referencias hasta que el migrador se reanude. La clave determinista permite reutilizarlo y verificarlo, pero no hay un recolector general de huérfanos B2.
- El adaptador no persiste el `VersionId` como parte del localizador normal. La referencia apunta a bucket y clave, no a una versión inmutable concreta.

### 3.3. Retención, versionado y eliminación

Custodia utiliza `ListObjectVersions` para la limpieza de objetos temporales. La eliminación se restringe a staging; el adaptador no proporciona una eliminación general de grabaciones originales.

La consulta de versiones usa `MaxKeys: 10` y falla cerradamente si la respuesta indica truncamiento. No es un proceso de limpieza de historial de versiones paginado ilimitado.

No he encontrado en el código de la PR una política de retención, lifecycle ni Object Lock. Tampoco un sistema de restauración de versiones anteriores para datos de usuario completos.

EP no ha implementado todavía retención, versionado ni eliminación de objetos B2. Su regla documentada es evitar borrados y sobrescrituras destructivas durante el MVP.

## 4\. Compatibilidad con Custodia

### 4.1. ¿Se puede reutilizar directamente el adaptador actual?

**No directamente.** El adaptador es técnicamente útil, pero está ligado a KHORA\:

- Exige el prefijo `khora/`\.
- Su validador `safeObjectKey()` rechaza claves fuera de ese espacio.
- Los localizadores B2 se validan contra el bucket y la región configurados para KHORA.
- `putEncryptedObject()` exige el sobre KHC1.
- Los nombres de variables de entorno son específicos de KHORA.
- El módulo es parte de `khora-web`; no está publicado como una librería independiente ni ofrece todavía un contrato genérico para otros frentes.

Por ello, EP no podría usarlo directamente para escribir `ep-ocp/` ni podría reutilizar su cifrado sin adoptar deliberadamente KHC1.

### 4.2. ¿Se puede compartir infraestructura B2?

**Sí, técnicamente.** Un mismo bucket B2 puede contener prefijos separados y cada aplicación puede utilizar una Application Key restringida a su prefijo.

Una distribución viable sería\:

| Dominio | Bucket | Prefijo | Clave |
|--------|--------|--------|--------|
| Custodia | `OCP-MCP` como destino compartido futuro, sujeto a validación y decisión | `khora/` | Clave restringida a `khora/` |
| EP | `OCP-MCP` | `ep-ocp/` | Clave restringida a `ep-ocp/` |

Esto no significa que hoy estén compartiendo un bucket. La PR \#348 exige un bucket de prueba aislado para el E2E y todavía no acredita su provisión. Tampoco está revalidada la cuenta B2 de EP ni la clave `ep-ocp`\.

**No se debe compartir una única clave con acceso amplio a ambos prefijos.** La separación de credenciales debe hacerse en Backblaze, no confiar únicamente en validaciones dentro de la aplicación. \[[Cloud Storage Application Keys](https://www.backblaze.com/docs/cloud-storage-application-keys?utm_source=chatgpt.com); [Map IAM Policies and S3 ACLs to Backblaze B2 Access Controls](https://www.backblaze.com/docs/cloud-storage-map-iam-policies-and-s3-acls-to-backblaze-b2-access-controls?utm_source=chatgpt.com)\]

### 4.3. Cambios mínimos para reutilización

La integración correcta sería separar el transporte de la lógica de dominio\:

**Capa compartida de transporte B2**

- Configuración de endpoint, región y bucket.
- Autenticación con Application Keys restringidas.
- `put`, `get`, `head`, `list`, verificación y operaciones de versiones.
- URLs firmadas de corta duración.
- Soporte para streaming y cargas multipart reanudables.
- Paginación completa sin límite artificial de 10 000 elementos.
- Localizadores que acepten un prefijo configurado, no un `khora/` hardcodeado.

**Capa Custodia**

- Conserva KHC1, `X_KHORA_KEY`, referencias de audio y ledger Neon.
- Mantiene el backfill Blob → B2 y las actualizaciones transaccionales.
- Conserva su política de acceso y limpieza de staging.

**Capa EP**

- Define `ep-ocp/`, identificadores lógicos de datasets, manifiestos, snapshots, sincronización, conflictos y restauración.
- Mantiene fuera de B2 la autoridad documental y el ledger operativo del OEP.
- Define su propia política de cifrado y secretos.
- Demuestra recuperación completa en una segunda ubicación.

No es recomendable importar `object-storage.ts` de `khora-web` directamente a EP. Conviene extraer el transporte común a un módulo reutilizable y mantener wrappers separados por dominio.
