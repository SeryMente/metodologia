## Inventario y brecha técnica consolidada

La candidata observada contiene 15 tablas SQLite, un índice de eventos y triggers de inmutabilidad para `events` y `receipts`. La ruta de datos prevista es `%LOCALAPPDATA%\SeryMente\OCP MCP\data\ocp-mcp.sqlite`; los paquetes locales quedan en `backups\<backup_id>.ocpbak`. El ZIP y el registro cliente MCP `stdio` son dependencias externas a la DB.

El backup usa SQLite Online Backup API (`SqliteConnection.BackupDatabase`) a staging, `PRAGMA quick_check`, SHA-256 y AES-256-GCM; la DEK del paquete se protege con DPAPI `CurrentUser`. La restauración requiere recuperar `backup_points.package_path`, una ruta absoluta almacenada en la misma DB que se intenta reponer. Por ello el `.ocpbak` actual no es una restauración autónoma desde cero.

DPAPI `CurrentUser` protege además las DEKs de `canonical_sources` y `snapshots`, la clave de autoridad HMAC y la clave privada Ed25519 de recibos. `installation.operator_sid` ata la raíz local al SID de origen. No existe un mecanismo implementado que re-envuelva todas las claves para un nuevo perfil. El test de ida/vuelta de la candidata ocurre en su fixture y no demuestra portabilidad.

La cadena de eventos es SHA-256 encadenada; los recibos usan firma Ed25519. Una migración debe preservar verificación de recibos históricos y la cadena, conservar la clave pública histórica, re-envelopar claves y revocar grants/request no consumidos del SID anterior. No se manipularon DB real, DPAPI blobs, credenciales ni claves durante este ciclo.

## Propuesta longitudinal de recuperación (NO APROBADA / NO IMPLEMENTADA)

Se propone separar el paquete de recuperación portable del backup local `.ocpbak`:

1. `manifest.json` externo, versionado, sin secretos: ID/fecha, versiones de producto/código/RID/esquema, rutas relativas seguras, tamaño y SHA-256 de cada artefacto, algoritmo/AAD, parámetros KDF/salt y hash del envelope.
2. `snapshot.sqlite.enc`: snapshot SQLite online cifrado AES-256-GCM bajo una PMK aleatoria por paquete.
3. `recovery-envelope.bin`: PMK envuelta por AES-256-GCM con una KEK derivada mediante Argon2id de una frase de recuperación introducida interactivamente. El proyecto ya referencia BouncyCastle.Cryptography 2.7.0, pero no se ha verificado implementación/build Argon2id.
4. `recovery-map.enc`: mapa cifrado bajo PMK con DEKs de `canonical_sources` y `snapshots`, clave HMAC activa y privada Ed25519, identificadas por objeto/purpose/version.
5. Restore desde manifiesto (no desde `backup_points` de la base origen): verificar paths/size/SHA; desbloquear PMK; autenticar/descifrar; ejecutar `integrity_check` y `foreign_key_check`; re-envelopar todas las claves DPAPI `CurrentUser` en el destino; actualizar SID; revocar grants/request pendientes del SID antiguo; preservar identidad de instalación, clave pública, recibos históricos y hash chain; swap con rollback con servicio detenido; validar readiness, diez herramientas MCP y smoke funcional read-only.
6. Mantener el `.ocpbak` actual separado y compatible. No sustituir Git como fuente canónica.

La frase de recuperación nunca se guarda en Git, manifiesto, B2, CLI args, variables de entorno o logs; se mantiene fuera de banda y separada del paquete. Su pérdida implicaría pérdida de recuperación portable.
